# 15. セキュリティ設計

## 1. 脅威モデル概要

Agentiaはローカル開発者マシンで動作し、Claude Codeの実行内容(ファイルパス・コマンド・場合によりプロンプト文面)という**機微になりうる開発情報**を扱う。主な脅威は「外部公開範囲の意図しない拡大」と「機微情報のログ蓄積」である。

## 2. ネットワーク境界

| 項目 | 既定 | 理由 |
|---|---|---|
| Ingest/REST/WSサーバーのバインドアドレス | `127.0.0.1`のみ | 同一マシン外からのアクセスを遮断。誤って社内LANに露出させない |
| リモート監視を有効化する場合 | `AGENTIA_ALLOW_REMOTE=true` + `AGENTIA_ACCESS_TOKEN`必須 | 明示的なオプトインを要求し、既定で安全側に倒す |
| WebSocket接続 | トークン有効時は`?token=`クエリを検証、無効な場合は`4401`でclose | 未認可クライアントの傍受防止 |

## 3. Hookコマンド実行の安全性

- `.claude/settings.json`に登録するコマンドは、リポジトリ同梱の署名済みCLI(`agentia-hook`)のみを想定し、ユーザーが任意のシェル文字列を評価しない設計とする(Hook自体はClaude Code側の機能であり、Agentiaはその出力を受動的に受け取るのみ)。
- Hook Forwarderはstdinから受け取ったJSONをそのままパースするのみで、`eval`やシェル経由の再実行を一切行わない(コマンドインジェクション面の排除)。
- `POST /internal/events`の受信データはZodスキーマで厳格にバリデーションし、想定外のフィールド・型は破棄する。

## 4. プライバシー配慮

| データ | 既定の扱い |
|---|---|
| `UserPromptSubmit.user_input`(ユーザーの指示文面) | UIには要約(「ユーザーから指示を受信」)のみ表示し、生文面は既定非表示。設定でオプトイン表示可能(`08_SCREEN_DESIGN.md` 7章) |
| ファイルパス・コマンド文字列 | そのまま表示(可視化の中核情報のため)。ただし将来的に秘匿ディレクトリ(`.env`等)のマスキングオプションを検討 |
| 生Hookペイロード(`raw`) | ログ保持期間を他フィールドより短く設定可能にし、エクスポート時は既定で除外 |
| 外部送信 | MVP・Phase2ではローカル内で完結。GitHub連携(Phase3)導入時も、送信先はユーザーが明示登録したリポジトリのWebhookのみ |

## 5. 認証・認可(将来のマルチユーザー化時)

- 現状は単一ユーザー・単一マシン運用のためログイン機構は無し。
- 将来チーム共有ダッシュボード化する場合は、APIキーベースの認可層を`14_BACKEND_DESIGN.md`のRESTレイヤーに追加し、WebSocket接続にも同トークンを要求する設計に拡張する(現行のトークン機構をそのまま昇格利用できるよう先行設計済み)。

## 6. 依存パッケージ・サプライチェーン

- `npm audit` / Dependabotを有効化し、Hook Forwarderという「Claude Codeから実行されるコード」の依存関係は特に最小限に保つ(攻撃対象領域の縮小)。
- Hook Forwarder自体はネットワークの外向きPOSTのみを行い、外部からの入力(stdin以外)を受け付けない。

## 7. XSS/インジェクション対策(フロントエンド)

- アクティビティログやキャラクターの`message`・`target`はユーザー/リポジトリ由来の文字列(ファイル名等)を含みうるため、Reactの標準エスケープに委ね、`dangerouslySetInnerHTML`は使用しない。
- 統計・API応答はすべてJSONとして型検証後に描画する。

## 8. セキュリティレビュー方針

- 実装フェーズでは`security-review`スキル相当のチェックを、Hook受信API・GitHub Webhook受信API(将来)・設定書き込みAPI(`/api/connection/setup`、ファイルシステム書き込みを伴う)を重点対象に実施する。
